# Архитектура проекта

VOSTERA состоит из **трёх независимых PHP-сервисов**, материалов оформления и будущего игрового сервера. Сейчас они не используют общую систему учётных записей и не требуют общей базы данных.

```text
Vostera-RP/
├── Сайт/                 Главная, новости, мониторинг UDP
│   ├── api/              Публичное JSON API мониторинга
│   ├── config/           Настройки сайта и игровых адресов
│   ├── includes/         Общие функции, SA-MP query
│   ├── assets/           Стили, JS, изображения
│   └── tests/            Тест парсера UDP
├── Форум/
│   ├── public/           Единственный публичный корень форума
│   ├── private/          Настройки и хранилище данных (закрыто от HTTP)
│   └── tools/            Подготовка установки
├── Вики/
│   ├── public/           Единственный публичный корень Wiki
│   ├── private/          Данные, настройки, логика (закрыто от HTTP)
│   └── tools/            Установка и миграция
├── Мод/tools/            Предварительная диагностика Pawn
├── Оформление/           Медиафайлы проекта
├── tools/                Проверки и тесты репозитория
└── .github/workflows/     GitHub Actions
```

## Что работает независимо

- **Сайт:** PHP с собственной конфигурацией `Сайт/config/site.php`. Мониторинг спрашивает SA-MP/open.mp-сервер по UDP; отсутствие ответа не заменяется придуманным онлайном. Платёжный магазин пока не является рабочим платёжным шлюзом.
- **Форум:** самостоятельный PHP-форум с собственными пользователями и файловым хранилищем. Он не является XenForo.
- **Wiki:** самостоятельная база знаний с собственными администраторами и файловым хранилищем. Она не является Chatwoot.
- **Мод:** в открытом GitHub пока только инструменты диагностики. Наличие веб-сервисов не доказывает работоспособность игрового клиента или сервера.

## Принципы изменений

1. Сохранять независимое развёртывание компонентов. Не переносить `private/` в `public/`.
2. Изменение формата данных сопровождать обратной совместимостью, миграцией и резервной копией.
3. Не публиковать файлы аккаунтов, токены, платёжные ключи, реальную серверную конфигурацию и клиентские ресурсы сомнительного происхождения.
4. Для новых функций добавлять тесты и указывать, что **не проверялось** в реальном сервере.
5. Для публичного запуска файловые хранилища форума и Wiki требуют оценки нагрузки, мониторинга и плана резервного копирования.
