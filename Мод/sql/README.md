# MariaDB — фундамент аккаунтов и экономики VOSTERA

Это **заготовка** для нового оригинального игрового прототипа, а не работающая игровая авторизация. Код Pawn сейчас **не подключён** к MySQL-плагину; все деньги и профессии в игре остаются сессионными.

## Что реализовано

- `001_accounts.sql` — уникальные аккаунты, поле современного хеша пароля, статус блокировки, кошелёк, выполненные работы и последняя выплата.
- `002_awards.sql` — процедура `vostera_award_job` с атомарной транзакцией InnoDB и блокировкой строк `FOR UPDATE`.
- Фиксированные суммы: **курьер $125**, **механик $100**. Клиент не может задать сумму.
- Уникальный идентификатор игровой операции (UUID) не позволяет оплатить одно событие дважды, даже при повторной отправке.
- Время предыдущей оплаты хранится в базе; после полноценного подключения аккаунтов задержка **90 секунд** сможет переживать переподключение и перезапуск сервера.
- Проверяются блокировки аккаунта, лимит денег (2 млрд), отсутствие прогресса и некорректные события.

## Развёртывание

Используйте отдельную базу **MariaDB 11.4+** с `utf8mb4`, отдельную учётную запись мигратора и резервные копии. Применяйте SQL из корня проекта:

~~~bash
mariadb -h 127.0.0.1 -u vostera_migrator -p vostera_dev < Мод/sql/001_accounts.sql
mariadb -h 127.0.0.1 -u vostera_migrator -p vostera_dev < Мод/sql/002_awards.sql
~~~

Запускать `Мод/tests/test_mariadb.sh` **на рабочей базе запрещено**: тест создаёт синтетические записи и изменяет их баланс. GitHub Actions поднимает одноразовый сервис MariaDB, использующий только тестовые учётные данные.

## Статусы процедуры

| Результат | Значение |
| --- | --- |
| `awarded` | Выплата проведена, журнал и прогресс обновлены |
| `duplicate` | UUID события уже был оплачен |
| `cooldown` | Не прошло 90 секунд с предыдущей выплаты |
| `forbidden` | Аккаунт удалён или заблокирован |
| `no_progress` | Не создана запись прогресса |
| `wallet_limit` | Превышен лимит кошелька |
| `invalid` | Некорректный UUID или профессия |

## Граница безопасности

Это **не публичный API**. Игрокам нельзя открывать доступ к MariaDB или процедуре. Вызывать её должен только доверенный сервер **после подтверждённой авторизации игрока и проверки выполнения маршрута или ремонта**. Процедура не проверяет геолокацию игрока и не заменяет игровую проверку.

Пароли должны храниться как современные односторонние хеши (например, Argon2id), созданные доверенным серверным компонентом. Не храните открытые пароли, не применяйте MD5, не используйте отображаемый ник вместо проверки личности.

**Ещё предстоит:** проверить совместимость MySQL-плагина с open.mp, реализовать регистрацию и вход, ограничение попыток, безопасную сессию, подготовленные SQL-запросы, callback/session generation, привязать UUID события к фактическому завершению работы и протестировать повторный вход.

Наличие схемы и успешных SQL-тестов **не означает**, что персонажи уже сохраняются в игре.
